# dsh-launcher v0.3.0 重构规划 / Tracking Plan

> 本文档是 v0.3.0 大版本重构的**追踪文档**：记录整体架构设计、各模块方案、边缘情况策略、优先级、被拒/降级清单与验收标准。已实现项以 **✓** 标注；未标注项为规划中的 P2 储备或被拒清单。
>
> 目标版本基线：v0.2.5。与上次工作区事故丢失的文档改动相衔接，本次重建并据实现代码核对更新。

---

## 一、总体目标 / Goals

v0.3.0 不是功能堆叠，而是一次**底座重构**，围绕四个主题：

1. **可观测性统一**：一份日志、一套错误码、一键诊断，让"出问题 → 定位 → 汇报"不再靠猜。
2. **更省心的环境管理**：Node 缺失自动补齐、dsh 更新静默延迟应用、配置自动回退，尽量少打扰用户。
3. **更强的稳健性**：崩溃后有僵尸清理与孤儿收养、窗口位置容灾、托盘按需出现。
4. **更清楚的数据边界**：卸载/清理只碰启动器自有数据，绝不越界触碰 dsh 生态。

## 二、架构设计 / Architecture

- **单一进程 + 单一数据目录**：壳（`DshWeb.exe`）与 dsh 服务仍是两个进程，但所有**自有状态**收敛到 `DSH_HOME\dsh-launcher\`（默认 `~/.dsh\dsh-launcher\`），与 dsh 生态（`profiles/`、`settings.yaml` 等）在目录层面严格分界。
- **一份日志文件**：`DSH_HOME\dsh-launcher\dsh.log` 同时承载壳的结构化 JSON Lines 与 dsh 服务原始输出 append 共存；日志所有权唯一归属壳（启动早期轮转），`start-dsh.vbs` 不再截断/轮转，消除双写者的所有权冲突。
- **错误码作为统一契约**：弹窗（用户可见）、结构化日志（code 字段）、诊断导出（按码汇总）共用同一套 `E####` 码，一个码贯穿"用户看到 → 日志留痕 → 汇报定位"全链路。
- **非侵入式更新**：更新永远"先下载、后应用、绝不打断当前会话"；下载与运行环境完全隔离（staging 目录），应用只在下次启动拉起服务之前进行。
- **便携 Node 免污染**：缺失时下载到用户目录（`%LOCALAPPDATA%`），只改进程级 PATH，不碰系统环境变量与注册表。
- **克制原则贯穿全局**：无第三方日志库、无遥测、无自制下载管线（npm 当下载器）、不做错误框架与本地化矩阵。

## 三、模块方案 / Module design

### 3.1 统一日志 ✓

**目标**：单一文件 `DSH_HOME\dsh-launcher\dsh.log`，替代旧 `shell.log` 与 `%USERPROFILE%\.dsh-web*.log` 的多文件方案。

- **格式**：壳写 JSON Lines（`ts` / `level` / `pid` / `code?` / `msg` / `ctx?`）；dsh 服务原始输出与 `[start-dsh] using ...` 行由 `start-dsh.vbs` append 追加同文件共存。
- **级别**：`Info` / `Warn` / `Error`；`DSH_LOG_LEVEL`（`INFO`/`WARN`/`ERROR`，兼容 `WARNING`）控制最小输出级别。
- **轮转**：所有权唯一归壳。判定（纯函数，可单测）：文件 >30MB 或最后写入 >3 天 → 滚动 `dsh.log → .1 → .2`，保留 ≤3 份；超 30 天的滚动旧档顺手清除。在启动早期、拉起服务前执行。
- **失败克制**：目录创建失败/写失败/轮转失败一律静默，日志故障绝不能影响启动。
- **服务侧**：`start-dsh.vbs` 收到 `DSH_LOG`（指向统一日志）后以 **append 模式（8）** 写入，**不截断、不自己轮转**；若日志被运行中服务锁定或缺失，回退 `%TEMP%\dsh.log` 优先保证冷启动成功。
- **旧文件**：`shell.log` 与 `%USERPROFILE%\.dsh-web*.log` 不再产生，存量旧文件由卸载清理（见 3.10）。

**验收标准（✓）**：单一 `dsh.log` 内同时看到壳的 JSON 行与 dsh 服务输出；启动时历史大文件被正确轮转到 `.1/.2`；旧日志路径不再有新文件生成。

### 3.2 错误码 ✓

**目标**：所有用户可见错误弹窗带 `[E####]` 码，便于复制粘贴到 Issue 精确汇报。

- **目录**（`src/DshShell/ErrorCodes.cs`）：E1xxx 运行环境，E2xxx 服务/生命周期，E3xxx 端口/网络，E4xxx 更新/下载，E5xxx 诊断，E9xxx 内部。
- **典型码**：E1001 未检测到 Node、E2002 服务启动超时、E2003 启动日志报错、E2011 插件缺失配置降级、E3001 端口被占、E4001 更新下载失败、E4002 延迟更新应用失败等。
- **联动**：弹窗文本含码；结构化日志的 `code` 字段引用同一码；诊断导出按码汇总（见 3.9）。
- **克制**：不做错误框架、不做本地化矩阵、不无限增加码位；`Describe` 给出用户可读的一句话描述。

**验收标准（✓）**：诱导 E1001/E2002/E2011/E3001 任一场景，弹窗均含对应 `[E####]`，日志 JSON 的 `code` 字段一致，消息可 Ctrl+C 复制。

### 3.3 配置自动回退 / 插件降级 ✓

**目标**：dsh-launcher-lifetime 插件卸载后，壳自动忽略并抹除 `settings.json` 里残留的 `serviceLifetime`（回退"跟随窗口"），无需手动删 JSON。

- **检测**：`IsLifetimePluginInstalled` 核对任一 profile 的 `node_modules` 物理实体或 `package.json` 清单声明（`dependencies` / `dsh.profile.bundles`）；任何读取失败一律按"未安装"处理（安全默认：宁回退不多驻）。
- **决策**：`ResolveEffectiveLifetime` —— 插件缺失 → 忽略残留配置、返回 `ShouldPurge=true`（调用方幂等抹除失效字段）；插件存在 → 正常解析用户选择。
- **边界**：仅抹除 `serviceLifetime` 这一失效键，不动 settings.json 其余内容（例如窗口状态等壳自己的数据保留）。

**验收标准（✓）**：装插件→设"常驻"→卸载插件→重启壳，服务按"跟随窗口"运行，settings.json 内 `serviceLifetime` 字段被自动清除。

### 3.4 托盘按需显示 ✓

**目标**：托盘默认隐藏，避免常驻用户被无谓打扰。

- **显示条件**（满足任一即显示）：
  1. 检测到 dsh-launcher-lifetime 插件已安装（该插件设置页需要托盘入口）；
  2. 本会话有待通知的更新（更新气泡依赖托盘）。
- **默认**：无插件、无更新时不创建托盘图标（更省资源、不占据任务栏）。

**验收标准（✓）**：干净环境（无插件、无更新）启动不出现托盘；装了插件或收到更新推送时托盘出现。

### 3.5 dsh 非侵入式更新（延迟应用）✓

**目标**：更新不打断正在运行的服务，避免"点更新 → 服务被停 → 会话丢失"。

**流程**：
1. 检测到 dsh 新版 → 托盘气泡；
2. 点击确认 → 后台 `npm pack @deepseek-ai/dsh` 下载到 `DataDir\staging`，**不触碰运行中环境**；
3. 下载成功 → 写 `pending-update.json`（固定具体版本，非 `latest`，消除"检测→应用"漂移）；
4. **下次启动拉起服务前**自动应用（`npm install -g` 固定版本）；
5. 失败/未完成不阻塞启动，继续用当前版本。

**边界**：下载失败（E4001）/应用失败（E4002）均可重试；`~/.dsh\dsh-launcher\pending-update.json` 损坏按无记录处理（下次转 latest 也可接受）。

**验收标准（✓）**：确认更新后当前会话服务不受影响；重启后服务以新版本拉起；staging 下载失败不阻塞本次启动。

### 3.6 Node 便携自动补齐 ✓

**目标**：未检测到 Node.js 时自动补齐，不让用户卡在"环境要求"门口。

- **解析唯一"Node/npm 本位"**：`PATH` → 注册表（HKLM/LWOW6432 的 Node.js InstallPath）→ 便携目录 `%LOCALAPPDATA%\dsh-launcher\env\node`；系统 Node ≥18 优先（尊重用户环境），否则便携。
- **补齐流程**：检测不到 → 一次性确认框（E1002 取消）→ 下载 LTS 便携版 zip（固定版本表，默认 `v22.16.0`，可用 `DSH_NODE_VERSION` 覆盖）→ SHA256 校验（SHASUMS256.txt，防供应链篡改，E1004）→ 解压到便携目录（E1005）。
- **镜像回退链（静态）**：`DSH_NODE_MIRROR` 自定义 → 上次成功镜像 → `nodejs.org` → `npmmirror`；上次成功镜像记入 `runtime-state.json` 的 `lastNodeMirror`。
- **免污染**：只将便携目录**前插进程级 PATH**（wscript → cmd → dsh/npm 自动继承），不改系统环境、不装进 $ProgramFiles、不注册表。便携目录放 `%LOCALAPPDATA%` 使 MSI 卸载也不误删。
- **克制**：不静默下载、不常驻重试、失败一次性报错；**不打包 Node 进安装包**。

**验收标准（✓）**：卸载/隐藏系统 Node 后启动 → 一次性确认 → 自动下载并拉起；校验和不一致被拒绝并报 E1004；设置 `DSH_NODE_MIRROR` 走自定义镜像。

### 3.7 僵尸进程清理 + 孤儿健康校验 ✓

**目标**：崩溃后不残留无人管理的 node 服务、不掉入"旧服务占着端口"的坑。

- **僵尸清理**：启动时读取 pid 文件记录的 PID，仅终止这些 PID 对应的残留进程；**绝不按进程名批量杀**（防误杀用户自启的其他 node）。
- **孤儿健康校验（HTTP 就绪）**：发现端口上有残留服务时：
  - 健康（HTTP 就绪）→ 接管、复用（含"跟随窗口"关窗时一并停掉）；
  - 坏状态（端口无 HTTP 响应）→ 清理并重新拉起（E2005 记录已清理）。

**验收标准（✓）**：强杀壳进程留下服务 → 重启壳后残留被清理或健康接管；pid 文件记录的 PID 之外的 node 进程不受影响。

### 3.8 窗口位置记忆 + 多显示器容灾 ✓

**目标**：窗口位置/大小跨会话保留，副屏变化时不至于窗口"消失"。

- **持久化**：位置/大小写入 `window-state.json`（`DSH_HOME\dsh-launcher\`）。
- **恢复策略**（纯函数 `RestoreWindowPosition`，可单测）：
  - 目标矩形与任一屏幕工作区有 ≥120×60 可见交集 → 采用并在该工作区内整格钳制（任务栏移动/工作区缩小后窗口仍完全可见）；
  - 完全越界（副屏拔掉等）→ 回退主屏工作区居中并钳制。

**验收标准（✓）**：窗口位置跨会话记忆；副屏拔掉后新启动在主屏居中且完全可见。

### 3.9 一键诊断导出 ✓

**目标**：`DshWeb.exe --diagnose [--min-level warn|error]` 一键打包脱敏信息，便于无脑汇报。

- **入口**：在 Main 最早期调用，不初始化 UI；产物写入系统"下载"文件夹（不可用回退用户目录），文件名 `dsh-launcher-diagnose-<yyyyMMdd-HHmmss>.zip`。
- **内容**：统一日志（默认全量尾部 3000 行；`--min-level warn|error` 按级别过滤 JSON 行 + 命中启动错误标志的原始服务输出行）、环境变量（DSH_* 白名单）、版本（node/npm/dotnet WindowsDesktop runtimes/WebView2 注册表）、settings.json、壳状态文件（window-state/pending-update/runtime-state/theme）、错误码汇总（每码次数 + 首条消息）。
- **脱敏**：用户目录路径替换为 `%USER%`（日志里常见路径泄漏用户名）。
- **边界**：绝不含 `.credentials.yaml` / 会话 / 存储 / 插件内容；产物由用户自主上传（延续"无遥测"承诺）。失败报 E5001。

**验收标准（✓）**：`DshWeb.exe --diagnose` 生成 zip；`--min-level error` 只含错误级内容；zip 内无凭据类文件、无明文用户名。

### 3.10 卸载清理 ✓

**目标**：卸载/清理只碰启动器自有数据，绝不越界触碰 dsh 生态。

- **MSI 卸载 CA（CleanUserData）**：只清理 `DSH_HOME\dsh-launcher\` 整目录（settings.json 残留、统一日志 dsh.log、window-state/pending-update/service-pid 等）与旧版 `%USERPROFILE%\.dsh-web*.log`；同时清理 pid 文件记录、仍存活的壳托管服务进程（只动我们记录的 PID）。任一失败跳过，不阻断卸载。
- **硬边界**：绝不触碰 `DSH_HOME` 下其余内容——`profiles/`、`settings.yaml`、`.credentials.yaml`、`sessions`、`storages`、插件等一切 dsh 生态数据。
- **便携版**：`uninstall-autostart.cmd -CleanData`（**显式可选**）做同样边界清理；不带参数只清自启/快捷方式，绝不 surprise-delete 用户数据。

**验收标准（✓）**：MSI 卸载后 dsh 生态数据完好、启动器自有数据清空；`uninstall-autostart.cmd` 不带 `-CleanData` 不清数据、带 `-CleanData` 才清自有数据。

## 四、边缘情况策略 / Edge-case policy

| 场景 | 策略 |
| --- | --- |
| 服务日志被运行中服务锁定 | `start-dsh.vbs` 回退 `%TEMP%\dsh.log`，保证冷启动成功（死冷启动比缺日志更糟） |
| 日志写失败 / 轮转失败 | 一律静默，日志故障不影响启动 |
| 插件清单损坏 / profiles 读取失败 | 按"插件未安装"处理，回退跟随窗口（安全默认） |
| 系统 Node 缺失 | 优先系统 Node ≥18，缺失才走便携；便携设 `%LOCALAPPDATA%` 使 MSI 卸载不误删 |
| 便携 Node 校验和不匹配 | 拒绝使用并删除（E1004，防供应链篡改） |
| 残留服务端口占用 | HTTP 就绪→接管复用；坏状态→清理重建（E2005） |
| 副屏拔掉 / 工作区变化 | 越界回退主屏居中 + 工作区钳制 |
| 更新下载 / 应用失败 | 不阻塞启动，继续用当前版本，可重试（E4001/E4002） |
| 取消便携 Node 安装 | 一次性报 E1002，不反复打扰 |
| 所有镜像下载失败 | 一次性报 E1003，不常驻重试 |

## 六、被拒 / 降级清单 / Rejected & downgraded

> 与上一版规划相比，以下方案经过评审被拒绝或降级，记录原因以避免重复论证。

- **主题 accent 增强** → **拒绝**。dsh 只有 dark/light/system 三档、无法读取自定义主题色做动态 accent，保持现状不动。
- **"镜像延迟测速选最快"** → **拒绝**。改为 **静态回退链**（自定义 → 上次成功 → nodejs.org → npmmirror），不做网络测速的复杂度。
- **"运行时静默装 .NET"** → **拒绝**。技术不可能：壳本身需要 .NET 才能运行，无法自我引导。改由 **MSI 链路 winget 引导**（P2 储备）。
- **SIGINT 优雅终止** → **降级为 P2 尽力而为**，不阻塞 v0.3.0。
- **自制下载管线** → **拒绝**。npm 当下载器（`npm pack` / `npx`），不自建带仓库逻辑的下载管线。
